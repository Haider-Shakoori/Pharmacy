# Pharmacy Android architecture

Batch 16 establishes the Flutter Android boundary for the pharmacy product.

## Toolchain

- Flutter 3.47.2 stable.
- Dart 3.13.2 through the pinned Flutter SDK.
- Android host generated with application ID `af.businessos.pharmacy`.
- Java 17 in CI.
- Flutter source lives under `mobile/` and has an independent CI gate.

## Current dependencies

The Batch 16 foundation pins current stable package lines for:

- Riverpod dependency/state boundary.
- GoRouter navigation.
- Flutter secure storage.
- Connectivity Plus.
- Device Info Plus.
- Package Info Plus.
- UUID generation.
- HTTP reachability probes.
- Flutter localization and Intl.

The Android host is generated by `mobile/tool/bootstrap_android.sh` using the pinned Flutter SDK so the Gradle wrapper/template stays aligned to Flutter itself. Native Android files will become committed/customized when native integrations are introduced (printing, device-specific capabilities, release signing).

## Architecture boundaries

`lib/app`
: application composition and routing.

`lib/core/config`
: compile-time environment values. No tenant URL is embedded by default.

`lib/core/storage`
: secure-storage interface. Future device credentials, refresh tokens and signed offline leases go here. The server signing private key must never exist in the app.

`lib/core/network`
: network-link observation and server reachability are separate concepts. A Wi-Fi/cellular link is not proof that the API is reachable.

`lib/core/device`
: stable installation UUID plus device/app metadata for later registration.

`lib/core/localization`
: English, Dari and Pashto application strings. Dari/Pashto use Flutter RTL behavior.

`lib/features`
: feature modules. The Batch 16 shell exposes POS, Stock, Customers and Sync surfaces without pretending later transactional functionality is available.

## Offline-first contract for future batches

Batch 17 introduces Drift/SQLite and the local entities needed to operate without the server.

Batch 19 must write a sale locally first. A normal API outage must not prevent a licensed offline sale.

Batch 20 synchronization must use:

1. connectivity detection;
2. server reachability;
3. entitlement/license refresh when possible;
4. authenticated device identity;
5. outbox push of critical local transactions;
6. server acknowledgements;
7. incremental pull;
8. conflict recording/resolution;
9. checkpoint update;
10. safe outbox compaction only after acknowledgement.

Transaction UUIDs and server idempotency are mandatory. Retrying an upload must not duplicate a sale, payment, stock movement or accounting posting.

## Security boundary

Secure storage is available from Batch 16 but contains no production secret yet. Later batches may store device credentials, tokens and signed offline license material. The platform private signing key remains server-only.

Subscription/license expiry may block new transactions after the authorized offline grace, but it must never delete local pharmacy data or prevent the app from reaching renewal/sync recovery surfaces.

## CI acceptance

The independent mobile workflow must pass:

- `dart format` check;
- `flutter analyze`;
- `flutter test`;
- clean Android debug APK compilation.

The mobile CI workflow bootstraps the Android host from Flutter 3.47.2 before these checks, making the build reproducible on a clean runner.
