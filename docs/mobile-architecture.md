# Pharmacy Android architecture

Batch 16 establishes the Flutter Android boundary for the pharmacy product.

## Toolchain

- Flutter 3.47.5 stable.
- Dart 3.13.4 through the pinned Flutter SDK.
- Android host generated with application ID `af.businessos.pharmacy`.
- Java 17 in CI.
- Flutter source lives under `mobile/` and has an independent CI gate.

## Three connection scenarios

The pharmacy app supports the same three connection choices as the restaurant
architecture: **Local**, **Cloud**, and **Automatic**.

### Local

The Android device connects directly to the pharmacy's Laravel/Apache server on
the same LAN/Wi-Fi. Staff may enter a private IP address or local hostname.
Private-network HTTP is accepted for this LAN path; public HTTP endpoints are
rejected. QR pairing and mDNS/nearby discovery can populate the same endpoint
later without changing the API contract.

### Cloud

The Android device connects to the pharmacy tenant's dedicated BusinessOS
Pharmacy endpoint over the Internet. Cloud endpoints must use HTTPS.

### Automatic

The app checks the Local endpoint first. If it is unreachable, it checks Cloud.
If neither is reachable, the app stays operational in offline state and later
syncs queued work. Local and Cloud modes themselves do not cross-fallback;
Automatic is the explicit failover mode.

Offline is not a fourth deployment mode. It is a runtime state available in all
three scenarios.

Both endpoints must expose the same versioned Pharmacy API. Transport switching
must never create a second business-data model. Batch 18 registration will bind
both endpoints to the same tenant/device identity before Automatic switching is
allowed for production transactions.

## Current dependencies

The Batch 16 foundation pins current stable package lines for Riverpod,
GoRouter, secure storage, Connectivity Plus, Device Info Plus, Package Info
Plus, UUID generation, HTTP probes, Flutter localization and Intl.

The Android host is generated by `mobile/tool/bootstrap_android.sh` using the
pinned Flutter SDK so the Gradle wrapper/template stays aligned to Flutter
itself. Native Android files will be committed/customized when native
integrations are introduced.

## Architecture boundaries

`lib/app`
: application composition and routing.

`lib/core/config`
: compile-time environment values. `API_BASE_URL` may seed the Cloud endpoint,
but no tenant URL is hard-coded by default.

`lib/core/storage`
: encrypted storage boundary for the selected connection profile and future
device credentials, refresh tokens and signed offline leases.

`lib/core/network`
: network-link observation, endpoint validation, three-mode route selection and
server reachability. Wi-Fi/cellular availability alone is never proof that a
server is reachable.

`lib/core/device`
: stable installation UUID plus device/app metadata for later registration.

`lib/core/localization`
: English, Dari and Pashto strings with RTL behavior.

`lib/features`
: feature modules. The Batch 16 shell exposes POS, Stock, Customers and Sync
surfaces without pretending later transactional functionality is available.

## Offline-first contract for future batches

Batch 17 introduces Drift/SQLite and the local entities needed to operate
without the server.

Batch 19 must write a sale locally first. A normal API outage must not prevent a
licensed offline sale.

Batch 20 synchronization must use connectivity detection, server reachability,
entitlement refresh, authenticated device identity, idempotent outbox push,
server acknowledgements, incremental pull, conflict handling, checkpoints and
safe compaction after acknowledgement.

Transaction UUIDs and server idempotency are mandatory. Retrying an upload must
not duplicate a sale, payment, stock movement or accounting posting.

## Security boundary

Secure storage contains the selected connection profile but no production
credential yet. Later batches may store device credentials, tokens and signed
offline license material. The platform private signing key remains server-only.

Subscription/license expiry may block new transactions after the authorized
offline grace, but it must never delete local pharmacy data or prevent renewal
and sync recovery.

## CI acceptance

The mobile workflow must pass `dart format`, `flutter analyze`, `flutter test`
and a clean Android debug APK build.


## Batch 17 — tenant-scoped local database

Drift/SQLite is the durable local store for Android. The database is scoped by
the pharmacy tenant identity, never by Local, Cloud or Automatic connection
mode. Switching transport therefore cannot create parallel inventories, sales
queues or sync checkpoints for the same pharmacy.

Before Batch 18 registration binds an installation to a tenant, the application
uses an `unbound` database scope. Transactional POS work is not enabled in this
state.

The initial local schema contains application metadata, medicine and batch
caches, customers, local sales, sale lines, payments, a durable synchronization
outbox and per-stream synchronization checkpoints. Money and quantity values
that require decimal precision are stored as exact decimal strings instead of
binary floating-point values.

The outbox uses a unique idempotency key as its primary key. This prepares Batch
20 retries without permitting duplicate logical events. Checkpoints are stored
per pull stream so catalog, inventory and other streams can advance
independently.

The native Drift executor is configured for WAL mode and can be shared across
isolates, preparing for later background synchronization. Batch 17 defines
storage and durability only: Batch 18 binds tenant/device identity, Batch 19
implements local-first sale transactions, Batch 20 implements network sync, and
Batch 22 enforces offline stock allocation.


## Batch 18 — mobile authentication and device registration

Batch 18 binds an Android installation to a real pharmacy tenant and an active
tenant user before transactional POS is enabled.

Registration requires the subscription license key, the installation UUID and
valid tenant-user credentials. The license and password are sent only for the
registration request and are not persisted on the device. The server first
resolves the license to its tenant, authenticates the user inside that tenant
database, then activates the device. Invalid credentials therefore do not
consume a device slot.

A successful registration returns an Ed25519-signed mobile access token plus the
existing signed offline lease. The access token is explicitly marked with
`purpose=mobile_access`, is bound to tenant, activation, user and installation,
and expires no later than the offline lease. Future API middleware must verify
the token purpose and current activation status before accepting synchronized
transactions.

The encrypted mobile registration record contains only the tenant/device
binding, signed tokens, expiry timestamps and display-safe user metadata. Drift
database scope is derived from the registered tenant ID. Changing Local, Cloud
or Automatic transport does not change that database scope.

Automatic registration tries Local first and Cloud second only for retryable
transport/server failures. Authentication or license validation failures do not
fall through to another endpoint. When the server returns the canonical cloud
tenant URL, the app stores it in the connection profile so later Automatic
failover stays on the same pharmacy.
